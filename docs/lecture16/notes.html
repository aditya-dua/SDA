Section 1: Why Alerts Matter

A dashboard is only useful if someone is looking at it. In a 24-hour streaming system, no one watches 24 hours a day. Alerts let the data come to you — instead of you going to the data.

Without alerts:
  10:47 PM  INFY price drops 6% — alert fires in stock_alerts
  10:47 PM  Nobody sees it
  11:30 PM  Risk manager checks Grafana manually — too late

With alerts:
  10:47 PM  Grafana alert fires → Slack message in #risk-alerts
  10:48 PM  Manager reviews position, takes action
ToolPurposeActs On
LoggingRecord everything that happenedEngineers debugging after an event
MonitoringShow current state continuouslyTeams watching dashboards
AlertingNotify when action is neededDecision-makers who need to respond

Key principle: The goal of an alert is to trigger a human action. If an alert fires and nobody knows what to do, the alert is not useful — it is noise. Every alert rule should have a corresponding runbook: who gets notified and what they do.

Section 2: Grafana Alert Architecture

Three Components

  1. Alert Rules — Conditions evaluated on a schedule. Each rule has a query and fires when the condition is met for a defined duration.
  2. Contact Points — Where notifications go. Supported: Email, Slack, PagerDuty, Opsgenie, Teams, Webhook, Telegram, and 20+ more.
  3. Notification Policies — Routing rules: which alert labels go to which contact point.

The Alert State Machine

NORMAL
→ condition met →
PENDING
→ "For" duration elapsed →
FIRING
→ condition clears →
RESOLVED

The "For" Duration — Why It Matters

Without a "For" duration, a single bad data point triggers an alert. With For: 2m, the condition must be true for 2 continuous minutes before the alert fires.

Without "For":
  Tick 1: Rs 1390 → FIRES immediately (bad tick? spike? genuine drop?)
  Tick 2: Rs 1410 → Resolves — false alarm. Engineers start ignoring alerts.

With For: 2m:
  Tick 1: Rs 1390 → enters PENDING state
  2 min later: still Rs 1385 → FIRES — genuine sustained move, worth acting on.

Section 3: Lab Part 1 — Create Alert Rules

Alert 1: "Too Many Open Alerts"

Navigate: Left sidebar → Alerting (bell icon) → Alert Rules → New alert rule

1

Name: Stock Alerts — High Open Count | Data source: MongoDB

2

Query: stock_alerts collection, match status=open, count

3

Condition: IS ABOVE 5 | Evaluate every: 1m | For: 2m

4

Labels: severity=warning, team=risk

5

Annotations: Summary: "Open alert count has exceeded threshold" | Description: "There are {{ $value }} unreviewed stock alerts."

Alert 2: "Symbol Price Anomaly" (from panel)

  1. Open the INFY Price panel → Edit → Alert tab → Create alert rule from this panel
  2. Condition: IS BELOW 1400 (absolute floor) | For: 1m
  3. Labels: severity=critical, symbol=INFY

Threshold design discussion: Should the threshold be absolute (Rs 1,400) or relative (5% from yesterday's close)? Absolute is simpler to configure. Relative is more accurate but requires the query to compute the deviation. The consumer_alerts.py from Lecture 9 already handles relative alerting at the Kafka layer — Grafana can handle the absolute floor as a safety net.

Section 4: Lab Part 2 — Contact Points

Option A: Email

Requires SMTP configuration in Docker. Add environment variables to the Grafana run command:

-e GF_SMTP_ENABLED=true
-e GF_SMTP_HOST=smtp.gmail.com:587
-e GF_SMTP_USER=your@gmail.com
-e GF_SMTP_PASSWORD=your-app-password

Then: Alerting → Contact points → New → Type: Email → Add your address → Test

Option B: Slack Webhook (Recommended for demos)

  1. Go to api.slack.com/apps → Create New App → Incoming Webhooks → Activate
  2. Add New Webhook to Workspace → select channel #grafana-alerts
  3. Copy webhook URL: https://hooks.slack.com/services/T.../B.../...
  4. Grafana: Alerting → Contact points → New → Type: Slack → Paste URL → Test

Notification Routing by Label

Alerting → Notification policies → Edit root policy → Add matchers:

  • severity = critical → Slack
  • severity = warning → Email
  • Default (catch-all) → Email

Section 5: Alert Design Framework

Three Questions for Every Alert Rule

  1. Who receives this alert and what will they do? If you can't answer in one sentence, the alert is not ready.
  2. What is the cost of a false positive? Each false positive erodes trust. After 10, people ignore alerts.
  3. What is the cost of a false negative? A missed alert on a financial system can mean regulatory exposure or monetary loss.
Notification CostExampleThreshold Approach
Low (Slack message, easy to dismiss)Warning — 5+ open alertsSensitive threshold OK
Medium (email + calendar)Price below floorThreshold needs care, use "For: 2m"
High (PagerDuty, on-call woken up)System outage, fraud spikeVery precise threshold, long "For" duration

Avoiding Alert Fatigue

Alert fatigue = when so many alerts fire that operators start ignoring them — including the ones that matter.

  • Set For: 2m or longer on non-critical rules — filters out single-tick blips
  • Delete any alert you can't write a runbook for
  • Use severity labels and separate channels (warnings vs critical)
  • Review and tune thresholds monthly — conditions change as data patterns change

Section 6: Case Studies

Case A: Zepto — Dark Store Operations

Zepto operates ~350 dark stores. Their alerting rules:

  • order_acceptance_rate < 90% for 3 minutes → Slack to store ops manager
  • avg_delivery_time > 35 min for 5 minutes → Escalation to city head
  • inventory_stockout_count > 20 SKUs → Automated reorder + alert

Discussion: Why is the "For" duration 3 minutes for order acceptance but 5 minutes for delivery time? What is different about the business consequence of each?

Case B: HDFC Securities — Trading Platform

  • price_feed_latency > 500ms → PagerDuty (on-call engineer, 24/7)
  • order_rejection_rate > 2% → Critical Slack + SMS to CTO
  • active_users_drop > 30% in 5 min → Infrastructure alert (possible outage)

Discussion: The order rejection rate alert goes to the CTO, not an engineer. Why? What does this tell you about how alerting functions as a business communication tool, not just a technical one?

Key Takeaways

✓ Key Takeaways — Lecture 16

  1. Alerts close the feedback loop — data flows in, decisions flow out. Without alerts, dashboards require 24/7 human watching.
  2. Three components: Alert Rules (conditions) → Notification Policies (routing) → Contact Points (delivery)
  3. The "For" duration prevents noise — require a condition to persist for 1–2 min before firing
  4. Every alert needs a runbook — who receives it, what they do. If you can't write this, the alert shouldn't exist.
  5. Alert fatigue kills alerting systems — fewer, well-calibrated, high-signal alerts outperform many low-quality ones
  6. Threshold design is a business decision — it depends on cost of false positives vs cost of missing a real event
