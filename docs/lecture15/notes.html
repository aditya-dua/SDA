Section 1: Dashboard Design Principles

The most common mistake: Building a dashboard that answers "What data do I have?" — instead of "What decision does this dashboard support?"

The Four Rules

  1. One question per panel, one job per dashboard. If a panel needs a paragraph to explain it, split it.
  2. Most important information top-left. Humans read dashboards like text — put your critical KPI there.
  3. Use colour to mean something, not for decoration. Green = normal, Amber = watch, Red = act. If everything is red, nothing is urgent.
  4. Refresh rate matches decision speed. Risk monitoring = 10s. Operations = 1 min. Executive = 5 min or manual.

Keep the fraud-rate Stat and review-queue Table from Lecture 14. Add the three panels below, then arrange all five into the target layout.

Panel 1 — Flagged Transaction Value (Stat)

Flagged Transaction Value
Business question: "How much money is currently associated with flagged transactions?"
SELECT SUM(amount) AS value
FROM transactions
WHERE is_fraud = 'true';

Settings: Visualisation = Stat | Unit = Indian Rupee | Decimals = 0 | Colour = red

Panel 2 — Daily Transaction Volume (Time Series)

Daily Transaction Volume
Business question: "How does transaction activity change across the month?"
SELECT
  $__timeGroupAlias(`timestamp`, '1d'),
  COUNT(*) AS value
FROM transactions
WHERE $__timeFilter(`timestamp`)
GROUP BY 1
ORDER BY 1;

Settings: Visualisation = Time Series | Unit = count | Line width = 2 | Fill opacity = 10

Panel 3 — Flagged Transactions by Merchant (Bar Chart)

Flagged Transactions by Merchant
Business question: "Which merchants generate the largest review workload?"
SELECT merchant, COUNT(*) AS value
FROM transactions
WHERE is_fraud = 'true'
GROUP BY merchant
ORDER BY value DESC
LIMIT 10;

Settings: Visualisation = Bar Chart | Category = merchant | Value = count | Orientation = horizontal

Panel 4 — Fraud Rate (from Lecture 14)

Flagged Transaction Rate
Business question: "What proportion of all transactions needs review?"

Reuse the Lecture 14 Stat query. Keep thresholds at green below 3%, amber from 3%, and red from 5%.

Panel 5 — Review Queue (from Lecture 14)

Highest-Value Flagged Transactions
Business question: "Which cases should analysts inspect first?"

Reuse the Lecture 14 Table query, sorted by converted amount descending and limited to 20 rows.

Discussion: A merchant with many flagged transactions is not automatically fraudulent. It may simply have high transaction volume. A manager should request a fraud-rate comparison before blocking the merchant.

Section 3: Lab Part 2 — Variables & Interactivity

Adding a City Dropdown

Variables make one dashboard reusable across locations instead of creating a separate dashboard for every city.

  1. Dashboard settings (gear icon) → Variables → New variable
  2. Name: city | Type: Custom | Values: Mumbai, Delhi, Bengaluru, Hyderabad, Chennai, Kolkata, Pune, Ahmedabad
  3. Enable Include All option and set the custom all value to .*.
  4. Add AND city REGEXP '^${city:raw}$' to queries that already have a WHERE clause.
  5. For queries without WHERE, add WHERE city REGEXP '^${city:raw}$' before GROUP BY.

The dropdown now filters all panels simultaneously. Selecting All uses the .* regular expression and keeps every city.

Saving & Sharing

  1. Save icon → name: "SDA — Fraud Operations"
  2. Share → Snapshot → generates a public link (no Grafana login required to view)

Section 4: Management Interpretation

Use the completed dashboard to prepare a 60-second fraud-operations briefing:

  1. State the risk: What is the flagged rate and flagged transaction value?
  2. Locate the workload: Which days, merchants, and cities dominate activity?
  3. Avoid overclaiming: Explain why flagged does not mean confirmed fraud.
  4. Recommend action: Name one investigation, control, or threshold change.

Section 5: Design Review Checklist

For each dashboard, evaluate:

QuestionWhat to Look For
Does it answer a clear business question?"Who is the user? What decision are they making?" — one sentence
Is colour usage consistent?Red = alert/bad, Green = normal. No decorative red on neutral data.
Is the refresh rate appropriate?30s is fine for demos; 5s for live risk monitoring
Are axes labelled with units?Always: ₹, count, %, minutes — never raw numbers without context
Is the time range visible?Users should always know what window of data they are looking at

Key Takeaways

✓ Key Takeaways — Lecture 15

  1. Start with the business question, not the chart type — "What decision does this support?"
  2. Most important KPIs top-left; main chart takes the most space
  3. Variables make dashboards reusable — one dashboard for all cities instead of duplicating
  4. Colour is communication — use thresholds intentionally; miscalibrated thresholds create alert fatigue
  5. Refresh rate = decision speed — match the refresh to how quickly the user needs to act
